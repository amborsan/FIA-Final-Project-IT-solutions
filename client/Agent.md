# Agent.md — Frontend AI agent contract

**This file is binding for every AI agent working on behalf of a frontend
developer in this project.** Read it before every task. If a request conflicts
with this file, stop and ask the frontend developer.

---

## 0. The one-line rule

> **You may change the frontend only. The backend belongs to the backend
> developer. If the backend must change, stop coding and create a backend request
> ticket for the backend developer.**

There is no exception to this rule. "It is a tiny change", "it is only one
field", "the demo is easier this way" and "I can fix it faster" are not
exceptions.

---

## 1. Who owns what

| Area | Owner | Your AI agent |
| --- | --- | --- |
| `server/` (Express, Prisma, migrations, seed, auth, API tests, `server/.env`) | **Backend developer only** | **Read-only at most. Never write.** |
| `docs/api.md`, `docs/database-erd.md`, `docs/architecture.md` | **Backend developer / team leads** | Read only. Never edit to make a frontend change fit. |
| `client/` | Frontend developers 1 and 2 | Your workspace |
| `docs/handoffs/tickets/FE-*.md` | Frontend requests, backend answers | You may create/update **your own ticket files** |
| `docs/handoffs/frontend-to-backend.md` | Shared index | Add a link only; do not rewrite backend decisions |

The backend developer is the **only** person allowed to implement backend
changes. Do not ask another frontend agent, another student or a general AI
assistant to do it either.

---

## 2. Absolute backend prohibitions

Never do any of the following:

- Edit, create, delete, rename, move or format anything in `server/`.
- Edit `server/prisma/schema.prisma`, migrations, seed data or generated Prisma
  files.
- Edit Express routes, controllers, middleware, auth, validation or server tests.
- Edit `server/.env`, `server/.env.example`, `server/package.json` or server
  dependencies.
- Run commands that write to the backend, including:
  - `prisma migrate`, `prisma db push`, `prisma db seed`, `prisma migrate reset`
  - `npm run db:migrate`, `npm run db:seed`, `npm run db:deploy`
  - direct `psql`/database changes
  - backend seed/reset scripts
- Start, stop or reconfigure the backend in a way that changes data or config.
  You may **use** the running API through HTTP.
- Add a second API, mock server, database layer, ORM or direct DB access inside
  the client to bypass the backend.
- Copy backend source into `client/` and change it there.
- Change `client/src/lib/api.ts`'s base URL, CSRF logic or cookie behaviour
  without the backend developer's written agreement.
- Invent API response shapes that are not in `docs/api.md` and then build
  production UI on top of them.
- Read `server/.env` or any secret. Never copy secrets into the frontend.
- Weaken security or privacy controls to make a screen work.

**Reading:** You may read `server/src` to understand the existing API and
`docs/api.md` to use it correctly. Reading is not permission to modify.

**Generated files:** Never edit `client/src/routeTree.gen.ts`. It is generated by
TanStack Router during `npm run dev` / `npm run build`.

---

## 3. What counts as a backend change

Stop immediately and create a ticket if a task needs any of these:

- a new endpoint, route or HTTP method;
- a new field, model, enum value or relation in the database;
- a changed response shape, field name, status value or error code;
- a changed permission/role rule or ownership rule;
- a new file upload/download rule;
- email, notification, invoice, PDF or export logic;
- server-side validation, sanitising, rate limiting or authentication changes;
- a bug that lives in `server/` (even if it looks small);
- anything that requires a backend command, migration or seed change.

If the existing API already supports the task, stay in `client/`. If you are not
sure, treat it as a backend change and ask first.

## 4. Required backend request workflow

1. **Stop coding the affected part.**
2. **Check `docs/api.md` and `docs/handoffs/frontend-to-backend.md`** to confirm
   the endpoint does not already exist.
3. **Create one ticket** in `docs/handoffs/tickets/` using
   `docs/handoffs/tickets/TEMPLATE.md`. Name it
   `FE-YYYYMMDD-short-title.md`.
4. Fill every field: page, problem, proposed endpoint, request body/params,
   expected JSON response, permissions, errors, acceptance criteria, priority
   and whether the frontend work is blocked.
5. Add a link to the ticket in `docs/handoffs/frontend-to-backend.md` under
   **Open tickets**.
6. **Tell the backend developer directly.** Only the backend developer can
   accept and implement it. Do not implement a workaround in production code.
7. Wait for status `IMPLEMENTED` (or `AGREED` with an explicit mock contract).
8. After implementation, update `client/src/lib/types.ts` to match the agreed
   response and continue the UI.
9. Update the ticket to say `FRONTEND CONSUMED` and move/link it under **Done**
   in the index.

### Ticket rules

- One ticket = one backend change.
- A ticket is not permission to modify the backend. It is a request.
- Do not edit a ticket's **Backend decision** section. Only the backend
  developer writes there.
- Do not use chat messages as the only record. The ticket is the source of
  truth.
- If blocked, show the ticket to the user; do not guess.

### Mock policy

You may build against a mock **only if** the backend developer writes
`AGREED MOCK` in the ticket with the exact JSON shape. The mock must live in the
frontend test/story layer, never in production API calls. Remove it when the real
endpoint is implemented.

---

## 5. Frontend work you can do without a ticket

- Pages, layouts, forms, tables, filters, empty/loading/error states.
- Components, styling, responsive fixes, accessibility.
- English/German translation keys.
- React Query usage of existing documented endpoints.
- Client-side validation that mirrors server rules (never replaces them).
- Tests for frontend logic.
- Documentation of frontend usage inside `client/`.

If an existing endpoint returns a field you need, use it. If it does not, ticket.

---

## 6. Language, design and security rules

- Every user-facing string must be added to **both** `en` and `de` in
  `src/i18n/translations.ts`. Never hardcode English or German UI text.
- Use `useI18n().t(...)`, `pick(record.nameEn, record.nameDe)`,
  `formatDate`, `formatMoney`.
- Use the existing DaisyUI theme and shared components. Do not add a second UI
  library, CSS framework or router.
- Keep pages usable at 360 px width.
- Never store authentication tokens in `localStorage`; the session cookie stays
  HTTP-only.
- Use `RichText` only for server-sanitised CMS HTML. Do not introduce other
  `dangerouslySetInnerHTML`.
- Use `downloadFile()` for protected files.
- No analytics, tracking pixels or non-essential cookies.
- Do not add dependencies without frontend team agreement. Never edit server
  dependencies.

---

## 7. Definition of done

Before reporting completion:

```bash
cd client
npm run lint
npm run build
npm run check:boundary   # fails if server/ files were changed
```

Also confirm:

- No file under `server/` changed.
- No `docs/api.md` / ERD / architecture edit was made to fit a UI.
- Any required backend change has a ticket and is not faked in production code.
- Both EN and DE were checked.
- No secrets or `.env` content in the diff.
- The user knows which ticket is waiting for the backend developer.

If `npm run check:boundary` fails, **revert the backend change** and create or
update the ticket. Do not "fix" the check.

---

## 8. Stop phrases

Use these when a backend change is needed:

> "This requires a backend change. I will not modify `server/`. I have drafted
> ticket FE-… for the backend developer and will continue with the frontend
> parts that do not depend on it."

> "The API does not return the field this screen needs. Creating a backend
> request instead of faking the data."

> "The bug is in `server/`. I am handing it to the backend developer with a
> reproduction ticket."

---

## 9. Quick reference

| Need | Action |
| --- | --- |
| New screen using existing API | Build in `client/` |
| New field from API | Ticket `docs/handoffs/tickets/FE-…` + tell backend dev |
| Bug in server | Ticket with reproduction + tell backend dev |
| Migration/schema change | Ticket, never run it |
| API contract changed | Read `docs/handoffs/backend-to-frontend.md`, update `types.ts` only after `IMPLEMENTED` |
| Unsure | Stop and ask the frontend developer/backend developer |
